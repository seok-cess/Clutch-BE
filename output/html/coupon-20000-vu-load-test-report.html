04Docker failure and native improvement

Docker 컨테이너에서 같은 규모로 실행했을 때는 6,216건이 dial: i/o timeout으로 종료됐다. 이는 품절 응답이나 로그 전송 실패가 아니라 신청 HTTP 요청이 상태 코드를 받지 못한 전송 실패였다.

05Interpretation and limitations

20,000 VU는 요청 20,000건이 완전히 같은 시각에 시작됐다는 뜻이 아니다. 60초 동안 VU가 점진적으로 증가해 최대 20,000명에 도달했고 각 VU가 한 번씩 신청한 조건이다.

이번 테스트가 확인한 범위

  • 고유 사용자 20,000명의 신청 요청이 모두 애플리케이션 응답으로 종료됐다.
  • 성공 10,000건과 품절 10,000건으로 재고 초과 발급이 없었다.
  • 전송 실패와 예상하지 못한 애플리케이션 응답이 없었다.
  • 관리자 API의 최종 발급 수량이 10,000건이었다.

별도 DB 검증이 필요한 범위

  • user_coupon과 SUCCEEDED 요청이 각각 정확히 10,000건인지
  • 오래 남은 PENDING 요청이 0건인지
  • 동일 사용자의 동시 중복 신청이 차단되는지
  • Outbox와 Kafka backlog가 최종적으로 해소되는지
  • 100만 사용자와 300만 발급 이력 전체 정합성

06Reproduction

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass -Force

.\k6\ramp\run-coupon-ramp.ps1 `
  -TotalVus 20000 `
  -CouponQuantity 10000 `
  -RampUpSeconds 60 `
  -TestId "coupon-native-20000-ramp60-run01"

실행 로그는 k6/logs/<TestId>.log에 저장되고 같은 Test ID가 Prometheus 태그로 기록된다.

이번 성공 결과의 Test ID와 원본 로그 경로는 공유된 출력에 없어 미확인으로 남겼다. 수치를 임의로 보완하지 않았다.

Final conclusion

Windows 네이티브 k6 환경에서 재고 10,000장, 고유 사용자 20,000명, ramp-up 60초 조건의 부하 테스트는 PASS했다. Docker 실행에서 발생했던 TCP 전송 실패는 네이티브 전환 후 재현되지 않았다.

이 결과는 과제에서 구체화한 20,000 동시 VU 쿠폰 발급 시연의 근거로 사용할 수 있다. 전체 데이터 정합성은 별도 DB 검증 결과와 함께 제시해야 한다.
