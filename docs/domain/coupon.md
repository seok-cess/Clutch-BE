# 쿠폰 발급 도메인 규칙

## 범위

이 문서는 쿠폰 이벤트 회차와 쿠폰 발급 요청에 적용되는 현재의 확정된 도메인 규칙을 설명한다.

## 주요 개념

- 쿠폰 이벤트: 쿠폰을 제공하는 이벤트의 정의
- 쿠폰 이벤트 회차: 이벤트가 실제 경기 상황에서 발동해 신청이 열린 한 번의 회차
- 쿠폰 이벤트 항목: 회차에서 발급할 수 있는 쿠폰 종류와 수량
- 쿠폰 발급 요청: 사용자가 특정 회차에 쿠폰을 신청한 기록

## 발급 요청 조건

- 쿠폰 이벤트, 이벤트 회차와 이벤트 항목이 모두 존재해야 한다.
- 이벤트 회차와 이벤트 항목은 요청한 쿠폰 이벤트에 속해야 한다.
- 이벤트 회차 상태가 `OPEN`이어야 한다.
- 현재 시각은 회차의 `openedAt` 이상이고 `expiresAt` 미만이어야 한다.
- `closedAt`이 설정된 회차에는 요청할 수 없다.
- 동일 사용자는 동일 이벤트 회차에 중복으로 발급 요청할 수 없다.
- 발급 성공 수량은 이벤트 항목의 총수량을 초과할 수 없다.
- 동시 요청에서도 중복 발급과 재고 초과가 발생하지 않아야 한다.

## 관리자 수동 오픈 테스트

- 수동 오픈과 활성 회차 조회 구현은 일반 경기 트리거 흐름과 구분해
  `com.clutch.coupon.test` 패키지에서 관리한다.

- 관리자는 경기 상태와 경기 트리거 발생 여부와 무관하게 대기 중인 쿠폰 이벤트를 수동으로 오픈할 수 있다.
- 수동 오픈은 기존 쿠폰 이벤트 정의와 쿠폰 항목을 사용해 새로운 `coupon_event_occurrence`를 생성한다.
- 수동 회차의 `matchEventId`, `gameTimeSeconds`, `sourceOccurredAt`은 설정하지 않는다.
- `openedAt`과 `detectedAt`은 관리자 요청을 처리한 UTC 시각이며, `expiresAt`은 이벤트의 `claimWindowSeconds`를 더한 시각이다.
- 수동 오픈 시 쿠폰 이벤트와 회차 상태를 모두 `OPEN`으로 변경한다.
- 같은 쿠폰 이벤트에 현재 신청 가능한 회차가 있으면 중복으로 오픈하지 않는다.
- 남은 쿠폰 재고가 없거나 이벤트 상태가 `READY`가 아니면 수동으로 오픈하지 않는다.
- 만료 시각이 지난 열린 회차는 `CLOSED`, 종료 사유 `EXPIRED`로 변경하고 해당 쿠폰 이벤트도 `CLOSED`로 변경한다.
- 수동 오픈된 이벤트에도 기존의 사용자 중복 발급과 재고 동시성 규칙을 동일하게 적용한다.
- 관리자가 이벤트 생성 시 트리거 종류로 `MANUAL_TEST`를 요청하면
  한국 날짜와 당일 저장된 마지막 순번을 조합한
  `MANUAL_TEST_yyyyMMdd_NNN` 형식으로 `coupon_event.trigger_type`에 저장한다.
- 수동 테스트 순번 생성은 기존 `coupon_event` 데이터를 사용하며 별도 순번 테이블을 두지 않는다.

## 활성 이벤트 조회

- 사용자 활성 이벤트 조회는 특정 경기와 연결하지 않는다.
- 현재 시각이 `openedAt` 이상 `expiresAt` 미만이고, 상태가 `OPEN`이며 `closedAt`이 없는 회차만 활성 회차로 본다.
- 동시에 여러 이벤트의 회차가 열려 있으면 가장 최근에 열린 회차 한 건을 반환한다.
- 활성 회차가 없으면 응답 본문 없이 HTTP 204를 반환한다.

## 데이터 정합성

- 사용자와 이벤트 회차 조합의 중복 요청은 데이터베이스 unique key로도 제한한다.
- 발급 요청 상태는 `PENDING`, `SUCCEEDED`, `FAILED`, `CANCELLED`를 사용한다.
- 사용자 쿠폰 상태는 `ISSUED`, `USED`, `EXPIRED`, `CANCELLED`를 사용한다.
- 현재 발급 경로는 요청을 `PENDING`으로 생성한 뒤 `SUCCEEDED` 또는 `FAILED`로
  전이한다. `CANCELLED` 요청은 기존 데이터 조회와 관리자 필터에서 안전하게
  처리하되, 실제 취소 유스케이스가 정해지기 전까지 새로운 상태 전이를 추가하지 않는다.
- 사용자 쿠폰의 저장 상태가 `ISSUED`여도 기준 시각이 `expiresAt` 이상이면 API 응답과
  상태 필터에서는 `EXPIRED`로 해석한다. 만료 상태를 맞추기 위한 일괄 갱신 배치는 두지 않는다.
- `USED`와 `CANCELLED`는 명시적으로 종료된 저장 상태이므로 만료 시각이 지나도 그대로
  유지한다. 쿠폰 사용과 관리자 취소는 모두 `ISSUED`이면서 `expiresAt` 이전일 때만 허용한다.
- 이벤트 항목의 `successCount`는 실제 발급 수를 비동기로 집계한 값이며 0 이상이고
  `quantity` 이하여야 한다. 재고 허용과 장애 복구 판단에는 사용하지 않는다.
- 애플리케이션 검증만으로 동시성 정합성이 보장된다고 가정하지 않는다.
- 동시성 제어 방식을 변경할 때는 경쟁 조건 테스트를 함께 확인한다.

## 발급 성공과 실패 보상

- Redis Lua 실행 성공은 재고와 당첨자 자리를 확보한 상태이며 최종 발급 성공이 아니다.
- 회차 오픈 시 Redis에 발급 단계, 혜택 스냅샷과 유효 시간을 함께 준비한다. 품절과
  중복 요청은 이 컨텍스트와 Redis Lua만으로 종료하며 MySQL을 조회하지 않는다.
- 발급 컨텍스트가 없거나 손상되면 DB 조회로 우회하지 않고 Redis 장애 복구가 완료될
  때까지 발급을 차단한다.
- `user_coupon`이 데이터베이스에 생성된 시점을 최종 발급 성공으로 정의한다.
- 발급 요청, 사용자 쿠폰과 발급 결과 Outbox는 하나의 MySQL transaction에서 처리한다.
- 사용자 쿠폰 생성이 완료된 뒤 발급 요청을 `SUCCEEDED`로 전이하고 응답에 발급된 쿠폰 식별자를 포함한다.
- 사용자 쿠폰 생성 전 오류가 발생하면 발급 요청을 rollback한다.
- MySQL transaction이 rollback되면 Redis에서 차감한 재고를 복원하고 당첨자 기록을 제거한다.
- 실패 보상이 완료된 사용자는 이후 발급 회차에 다시 참여할 수 있어야 한다.

## 쿠폰 종류 관리

- 쿠폰 종류는 `RATE`(정률 할인) 또는 `AMOUNT`(정액 할인) 혜택을 가진다.
- 정률 할인 값은 0보다 크고 100 이하여야 하며, 정액 할인 값은 0보다 커야 한다.
- 할인 값은 데이터베이스의 `DECIMAL(10,2)` 범위와 동일하게 정수 8자리와 소수 2자리 이하여야 한다.
- `ACTIVE` 상태의 쿠폰 종류만 신규 쿠폰 이벤트에 사용할 수 있다.
- 이미 이벤트에서 사용된 쿠폰 종류도 `ACTIVE`라면 다른 신규 이벤트에서 재사용할 수 있다.
- 이벤트에서 한 번이라도 사용된 쿠폰 종류의 이름, 할인 방식과 할인 값은 변경하거나 물리 삭제할 수 없다.
- 사용된 쿠폰 종류도 `INACTIVE` 전환은 허용하며, 기존 이벤트와 이미 발급된 쿠폰에는 영향을 주지 않는다.
- 사용되지 않은 쿠폰 종류만 혜택 정의 수정과 물리 삭제가 가능하다.
- 사용 중인 혜택을 변경해야 하면 기존 쿠폰 종류를 `INACTIVE`로 전환하고 새로운 쿠폰 종류를 생성한다.

## 현재 기술 범위

- Redis와 Lua script는 동시 요청의 재고 차감과 동일 회차 중복 당첨 방지에 사용한다.
- JPA와 MySQL transaction은 발급 요청, 실제 사용자 쿠폰과 발급 결과 Outbox의 원자적 저장에 사용한다.
- Kafka는 실제 쿠폰 생성을 결정하는 핵심 경로가 아니라 발급 결과 후속 전달에 사용한다.
- 기존 `coupon.claim.accepted` 소비 경로는 호환을 위해 유지하며 신규 발급 요청의 핵심 경로에서는 사용하지 않는다.
- 상세 결정과 대안은 `docs/adr/001-synchronous-coupon-issuance.md`와
  `docs/adr/003-async-coupon-success-count.md`를 따른다.
- 여러 애플리케이션 인스턴스가 실행되어도 성공 수량 집계는 MySQL named lock을
  획득한 한 인스턴스만 수행한다. 잠금을 얻지 못한 인스턴스는 해당 주기를 건너뛴다.

## 실시간 잔여 재고

- 사용자 잔여 재고 조회와 SSE 갱신은 Redis 재고를 기준으로 하며 갱신마다 MySQL을
  반복 조회하지 않는다.
- 재고 소진은 정상 상태로 `0`을 전달하고 Redis 키 누락 또는 조회 장애와 구분한다.
- 발급에 따른 SSE 알림은 실제 쿠폰 발급 transaction이 commit된 뒤 전송한다.
- SSE 재연결 시 Redis의 최신 스냅샷을 즉시 전달하여 연결 단절 중 놓친 상태를 복구한다.
- 상세 HTTP와 SSE 계약은 `docs/api/coupon-stock.md`를 따른다.

## Redis 재고 장애 복구

- Redis 연결 장애 또는 재고 키 누락을 감지하면 새 쿠폰 발급을 중단한다.
- 복구는 재고 키, 회차별 발급 사용자 목록과 발급 컨텍스트를 함께 재구축한다.
- 장애 중 발급 요청 순서는 보존하지 않으며 복구 후 다시 요청한다.
- 실제 `user_coupon`을 최종 발급 기준으로 사용한다.
- 복구 전에 성공 발급 요청 수와 실제 쿠폰 수를 비교한다.
- 값이 다르면 자동 복구를 중단하고 운영자 확인 전까지 발급을 재개하지 않는다.
- 검증을 통과하면 Redis 재고와 회차별 발급 사용자 목록을 함께 재구축한다.
- 상세 결정은 `docs/adr/002-redis-coupon-stock-recovery.md`를 따른다.
