# ADR-006: 쿠폰 정합성 검증을 비동기 실행하고 결과를 영속화

- Status: Accepted
- Date: 2026-08-30
- Decision Makers: 쿠폰 운영 담당자

## Context

대량 쿠폰 정합성 SQL은 완료까지 시간이 걸려 HTTP 요청 transaction 안에서 실행하기
어렵다. 여러 애플리케이션 인스턴스가 같은 MySQL을 사용하므로 중복 집계도 막아야 한다.
검증 도중 장애가 나더라도 운영 쿠폰 데이터는 변경하지 않고 실행 상태를 추적해야 한다.

## Decision

- 관리자 수동 요청만 지원하고 실행 ID를 `202 Accepted`로 즉시 반환한다.
- 전용 단일 스레드 Executor에서 검증하며, MySQL named lock으로 인스턴스 간 실행을 하나로 제한한다.
- POST의 `RUNNING` 확인과 이력 생성도 같은 lock으로 직렬화한다.
- 전체 집계는 `REPEATABLE READ`, read-only transaction에서 하나의 기준 시각과 일관 스냅샷을 사용한다.
- 결과와 완료·실패 상태는 검증 transaction 종료 후 별도 쓰기 transaction에 저장한다.
- 실행 이력은 자동 삭제하지 않고 항목별 판정과 집계만 저장한다.
- 비정상 종료 이력은 복구 유예시간이 지난 뒤, named lock을 획득한 인스턴스만 실패 처리한다.
- 상세 JSON을 보고서 데이터로 사용하고 서버 파일 보고서는 만들지 않는다.

## Alternatives Considered

### HTTP 요청에서 동기 실행

대량 집계 시간이 프록시와 클라이언트 timeout을 넘을 수 있고 연결을 불필요하게 점유한다.

### 인스턴스 로컬 플래그만 사용

단일 프로세스 중복만 막고 여러 인스턴스의 동시 실행을 차단하지 못한다.

### 스케줄 자동 실행

운영 부하가 큰 전체 집계를 서버가 임의 시점에 시작하게 되므로 현재 운영 요구와 맞지 않는다.

## Consequences

- 관리자는 실행 이력과 40개 결과를 재시작 후에도 조회할 수 있다.
- named lock 연결은 검증이 끝날 때까지 유지되고 정상·예외 경로에서 명시적으로 해제된다.
- 일관 스냅샷이 오래 유지되면 MySQL purge에 영향을 줄 수 있어 운영자는 저부하 시간에 실행해야 한다.
- 복구 유예시간 동안 비정상 종료 이력이 `RUNNING`으로 보일 수 있다.

## Follow-up

- 운영 데이터 증가에 따라 실행 시간과 DB 부하를 관찰한다.
- 증분 검증이나 별도 읽기 복제본이 필요해지면 별도 ADR로 결정한다.
