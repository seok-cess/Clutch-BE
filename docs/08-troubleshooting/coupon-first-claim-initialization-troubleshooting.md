# 새 쿠폰 회차의 첫 발급 요청 실패 트러블슈팅

## 한 문장 요약

Redis가 정상이어도 새 쿠폰 회차를 연 직후 Redis 재고 키를 만들지 않으면, 첫 발급
요청이 `503 COUPON_STOCK_NOT_INITIALIZED`로 실패한다. 이 상태를 실제 Redis 장애와
구분하고, 회차 오픈 뒤 즉시 재고를 초기화해야 한다.

## 증상

관리자가 쿠폰 이벤트 회차를 열었고 Redis 컨테이너도 정상 동작하는데, 첫 사용자의
쿠폰 발급 요청이 실패한다. 잠시 뒤에는 같은 회차의 발급 요청이 성공한다.

### 기대 동작

```text
쿠폰 회차 오픈 완료
→ Redis 재고 준비 완료
→ 첫 발급 요청도 HTTP 201 성공
```

### 현재 동작

```text
쿠폰 회차 오픈
→ Redis 재고 키 없음
→ 첫 발급 요청: HTTP 503 COUPON_STOCK_NOT_INITIALIZED
→ 애플리케이션 상태: UNAVAILABLE
→ 복구 스케줄러가 약 2초 뒤 Redis 재구축
→ 이후 발급 요청: 정상 처리 가능
```

첫 요청이 Redis를 동기 초기화하는 것이 아니다. 첫 요청은 실패하고, 그 실패가
복구 절차를 시작할 상태 전이를 만든다. 스케줄러가 실행되기 전 요청도 `503`으로
실패할 수 있다.

## 재현 조건

다음 조건이면 실제 Redis 장애 없이 재현된다.

1. Redis 서버는 연결 가능한 상태다.
2. 수량이 남아 있는 새 쿠폰 이벤트 회차를 연다.
3. 해당 이벤트 항목의 Redis 키 `coupon:event-item:{itemId}:stock`가 없다.
4. 회차 오픈 직후 발급 API를 호출한다.

```text
POST /api/v1/coupon-events/{eventId}/occurrences/{occurrenceId}/claims
X-User-Id: {userId}
```

## 원인 분석

### 1. 회차 오픈 흐름에 Redis 초기화가 없다

`CouponEventActivationService.manualOpen()`은 이벤트 상태와 회차를 DB에 저장하지만,
Redis 재고 키를 초기화하지 않는다.

### 2. Redis Lua가 없는 재고 키를 초기화되지 않은 상태로 반환한다

`redis/coupon-claim.lua`는 재고 키가 없으면 `-3`을 반환한다. 애플리케이션은 이를
`STOCK_NOT_INITIALIZED`로 해석한다.

### 3. 발급 서비스가 이를 장애 복구 상태로 전이한다

`CouponClaimService`는 `STOCK_NOT_INITIALIZED`를 받으면 복구 상태를 `UNAVAILABLE`로
바꾸고, 요청에는 `COUPON_STOCK_NOT_INITIALIZED`를 반환한다.

### 4. 장애 복구 스케줄러가 모든 열린 회차를 재구축한다

스케줄러는 Redis 연결이 가능한데 상태가 `UNAVAILABLE`이면 MySQL을 기준으로 열린
회차의 재고와 발급 사용자 Set을 재구축한다. 기본 실행 주기는 2초다.

## 실제 Redis 장애와의 차이

| 구분 | 새 회차 초기화 누락 | 실제 Redis 장애 |
|---|---|---|
| Redis 연결 | 정상 | 실패 또는 불안정 |
| 재고 키 | 새 회차에만 없음 | 일부 또는 전체 유실 가능 |
| 필요한 처리 | 새 회차 재고 준비 | DB 기준 정합성 검증 후 전체 복구 |
| 첫 사용자 요청 | 실패하면 안 됨 | 안전을 위해 503으로 차단 |

둘을 같은 흐름으로 처리하면 새 회차의 첫 사용자가 장애 복구를 대신 수행하게 된다.

## 영향

- 선착순 쿠폰에서 가장 먼저 요청한 사용자가 부당하게 실패한다.
- 초기 복구 전 들어온 요청도 `503`으로 실패한다.
- k6 부하 테스트에서 재고 소진 결과가 아니라 초기화 지연에 의한 실패가 섞인다.
- Redis 장애 복구 메트릭에 정상적인 회차 오픈이 장애처럼 기록될 수 있다.

## 해결 방식

발급 요청에서 초기화하거나 재시도하지 않는다. 회차 오픈 흐름은 DB 커밋 뒤 Redis
초기화를 등록한다.

```text
1. DB 트랜잭션에서 쿠폰 회차 생성
2. 트랜잭션 커밋 후 이벤트 항목 Redis 재고 키 초기화
3. 초기화 성공 후 발급 가능 상태로 노출
4. Redis 초기화 실패 시 상태를 `UNAVAILABLE`로 바꾸고 발급을 fail-closed로 유지
```

초기화는 기존 재고를 덮어쓰면 안 된다. 새 키에만 남은 수량을 넣는 원자적
`SETNX` 방식을 사용한다. 회차별 `claimed-users` Set은 발급 이력이 없으므로 비어
있는 상태로 시작할 수 있다.

실제 Redis 장애 뒤에는 기존의 MySQL 기준 전체 재구축 로직을 계속 사용한다.

## 검증 기준

수정 뒤에는 아래 테스트가 모두 통과해야 한다.

1. 회차 오픈 직후 Redis 재고 키가 이벤트 항목 수량으로 생성된다.
2. 오픈 직후 첫 발급 요청이 `201`으로 성공한다.
3. 초기화 메서드를 다시 호출해도 이미 차감된 Redis 재고가 증가하지 않는다.
4. Redis 연결 장애 중에는 발급 요청이 `503`으로 차단된다.
5. Redis 복구 뒤에는 MySQL 기준 재구축으로 남은 재고와 발급 사용자 Set이 복원된다.

## k6 부하 테스트와의 관계

30,000건 쿠폰 발급 부하 테스트 전에 아래의 작은 회귀 시나리오를 먼저 추가한다.

```text
재고 10장
서로 다른 사용자 100명 요청
기대값: HTTP 201 10건, COUPON_STOCK_EXHAUSTED 90건, 503 0건
```

이 시나리오가 통과한 뒤에만 다음 대규모 시나리오를 실행한다.

```text
재고 10,000장
서로 다른 사용자 30,000명 요청
기대값: HTTP 201 10,000건,
        COUPON_STOCK_EXHAUSTED 20,000건,
        기타 4xx/5xx 0건
```

최종적으로 MySQL 성공 발급 수, `user_coupon` 수, 이벤트 성공 수량, Redis 잔여
재고, Redis 발급 사용자 Set 크기도 기대값과 일치해야 한다.
