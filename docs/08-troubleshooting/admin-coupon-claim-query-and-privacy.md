# 관리자 쿠폰 발급 내역 조회와 개인정보 보호 트러블슈팅

## 문제 상황

관리자 발급 내역은 이벤트, 쿠폰 종류, 사용자와 실제 발급 쿠폰 정보를 함께 보여줘야 한다.
대량 이력에서 상세 테이블을 먼저 모두 조인하고 정렬하면 첫 페이지를 조회할 때도 넓은 범위의
조인과 정렬이 발생할 수 있다. 사용자 이름, 이메일과 전화번호 원문이 관리자 응답이나 로그에
노출될 위험도 함께 있었다.

## 원인

- 페이지 범위를 확정하기 전에 상세 테이블을 조인하면 조회 대상보다 많은 행을 처리한다.
- 모든 검색 조건에 같은 조인을 사용하면 필요하지 않은 테이블도 읽는다.
- 개인정보를 Entity와 조회 결과에서 그대로 응답하면 API와 로그 노출 경로가 늘어난다.

## 해결

### 조회 범위 선확정

`AdminCouponClaimQueryRepository`는 필터에 맞는 `coupon_claim_request` ID를 최신순으로 먼저
조회한다. `LIMIT`과 `OFFSET`으로 현재 페이지를 확정한 뒤 해당 ID에 대해서만 이벤트, 쿠폰
종류, 사용자와 실제 발급 쿠폰을 상세 조인한다.

ID 조회 단계에는 검색 조건에 필요한 테이블만 동적으로 추가한다.

- 이벤트명·트리거 검색: `coupon_event` 조인
- 쿠폰 상태 검색: `user_coupon` 조인
- 쿠폰 종류 검색: `coupon_event_item` 조인

목록과 전체 건수는 같은 필터 생성 로직을 사용해 서로 다른 조건으로 계산되지 않게 했다.
이벤트·사용자·기간 조회에는 Flyway로 추가한 복합 인덱스를 사용한다.

### 개인정보 노출 경로 축소

- `PersonalDataMasker`가 이름·이메일·전화번호를 응답 DTO로 변환하기 전에 마스킹한다.
- `User.toString()`은 개인정보 필드를 출력하지 않는다.
- 발급 이력이 있는 정책은 임의 변경·삭제하지 못하도록 서비스 규칙으로 제한한다.

## 검증

- 필터가 없는 조회는 발급 요청 PK를 역순으로 읽고 페이지 크기만큼 ID를 제한한다.
- 필터별로 필요한 조인만 추가되는지 Repository 테스트로 확인한다.
- 상세 조회가 선조회한 ID만 `IN` 조건으로 조인하는지 확인한다.
- 이름·이메일·전화번호의 정상값, 빈 값과 `null` 마스킹을 단위 테스트한다.
- 관리자 서비스 응답에 마스킹된 값만 포함되는지 검증한다.

## 남은 한계

번호형 페이지네이션의 큰 `OFFSET`은 뒤쪽 페이지로 갈수록 읽기 비용이 증가한다. 실제 운영
데이터에서 이 비용이 병목으로 확인되면 PK 기반 커서 페이지네이션을 별도 검토한다.
