# 20,000 VU 쿠폰 발급: Redis 선판단 트러블슈팅

## 한 문장 요약

대량 선착순 발급에서 MySQL의 공통 행 잠금은 제거했지만, 품절·중복 요청도 Redis에
도달하기 전 MySQL 메타데이터를 여러 번 조회하고 있었다. 회차 정보를 Redis에 준비해
품절·중복 요청을 DB에 보내지 않도록 바꿨다. 다만 단일 k6 발생기의 TCP 연결 실패가
남아 있어, 최신 20,000 VU 결과만으로 서버의 최종 한계를 판단할 수는 없다.

## 목표

재고 10,000장에 사용자 20,000명이 한 번씩 요청할 때 다음 결과를 기대한다.

```text
HTTP 201 발급 성공       10,000건
HTTP 409 품절 응답       10,000건
기타 HTTP/연결 실패          0건
MySQL user_coupon        10,000건
```

사용자는 발급 성공 응답에서 실제 쿠폰 ID를 즉시 받아야 한다. 따라서 전체 발급을
Kafka 또는 Redis Stream으로 비동기화하는 방식은 이번 범위에 포함하지 않는다.

## 1. 처음 발견한 병목: 공통 성공 수량 행 잠금

처음에는 Redis Lua가 재고와 중복 발급을 제어했지만, 성공한 모든 요청이
`coupon_event_item.success_count` 한 행을 갱신했다.

```text
Redis 당첨 5,000건
→ 5,000개 MySQL transaction
→ 같은 success_count 행 X-lock 경쟁
→ Hikari pending 증가
→ Tomcat 요청 적체와 timeout
```

10,000 VU·재고 5,000장 테스트에서 Hikari 20개 중 19개가 사용 중이었고, 대기 요청은
최대 178개였다. MySQL 행 잠금은 최대 2,914회/분, 잠금 대기 시간은 최대
1,115초/분까지 관측됐다.

### 조치

- 요청 transaction에서 `success_count` 증가를 제거했다.
- 성공 수량은 실제 `user_coupon` 수를 5초 주기로 집계하는 값으로 바꿨다.
- Redis 초기화와 장애 복구는 `success_count`가 아니라 실제 쿠폰 수를 기준으로 한다.

이 변경으로 발급 허용을 결정하는 MySQL 공통 행은 사라졌지만, 아직 모든 요청이
Redis 판단 전에 DB를 여러 번 읽는 문제가 남았다.

## 2. 남은 문제: 품절 요청도 MySQL을 먼저 조회했다

기존 요청 흐름은 다음과 같았다.

```text
20,000명 전원
→ 이벤트 조회
→ 회차 조회
→ 활성 단계 조회
→ 쿠폰 항목 조회
→ 혜택 스냅샷 조회
→ 기존 발급 요청 조회
→ Redis Lua 재고·중복 판단
```

따라서 최종적으로 품절될 10,000명도 Redis에서 즉시 끝나지 못하고, 공통 이벤트 정보를
읽기 위해 MySQL 연결과 쿼리를 사용했다. DB 쓰기만 줄인 상태에서는 이 읽기 부하와
Hikari 대기가 다음 병목이 될 수 있다.

## 3. 해결: Redis 선판단

회차를 열 때 아래의 발급 불변 정보를 Redis 컨텍스트로 저장한다.

- 이벤트 ID와 회차 ID
- 회차 오픈·만료 시각
- 시간대별 활성 쿠폰 항목
- 각 항목의 할인 유형과 할인 값

새 요청 흐름은 다음과 같다.

```text
요청
→ Redis 발급 컨텍스트 조회
→ 현재 활성 단계 선택
→ Redis Lua: 중복 여부 + 재고 확인 + 재고 차감 + 당첨자 기록
  ├─ ALREADY_CLAIMED / STOCK_EXHAUSTED
  │   → 즉시 409 응답, MySQL 조회·transaction 없음
  └─ SUCCESS
      → 짧은 MySQL transaction
         → coupon_claim_request 저장
         → user_coupon 저장
         → 결과 Outbox 저장
         → HTTP 201과 couponId 응답
```

### 정합성 보장

- Redis Lua 성공은 최종 쿠폰 발급이 아니라 DB 저장 전의 당첨 자리 확보를 뜻한다.
- 성공 요청의 DB 저장 transaction이 rollback되면 Redis 재고를 복원하고 당첨 사용자
  Set에서 사용자를 제거한다.
- Redis 컨텍스트·재고 키가 없거나 손상되면 DB로 우회하지 않고 `503`으로 차단한다.
  잘못된 재고로 발급하는 것보다 복구 뒤 재시도하게 하는 fail-closed 정책이다.
- Redis 장애 복구는 재고, 당첨 사용자 Set, 발급 컨텍스트를 MySQL 기준으로 함께
  재구축한다.

## 4. 20,000 VU 결과 해석

### 14:37 테스트

| 항목 | 결과 |
|---|---:|
| 발급 성공 | 10,000 |
| 품절 응답 | 2,415 |
| 연결 단계 실패 | 7,585 |
| 성공 요청 Claim p95 | 11.91초 |
| 실제 최대 VU | 18,967 |
| 최종 이벤트 집계 | 302 / 10,000 |

최종 이벤트 집계가 302건으로 보인 것은 당시 `success_count`가 비동기 집계값이었기
때문이다. 개별 저장 검증으로 실제 `user_coupon` 10,000건 저장은 확인됐다.

### 16:58 테스트

개별 쿠폰 조회를 제거한 뒤 수행한 결과다.

| 항목 | 결과 |
|---|---:|
| 발급 성공 | 10,000 |
| 품절 응답 | 1,209 |
| 연결 단계 실패 | 8,791 |
| 성공 요청 Claim p95 | 8.68초 |
| 실제 최대 VU | 17,748 |
| 최종 이벤트 집계 | 10,000 / 10,000 |

발급 성공 수량과 p95는 개선됐지만, 전체 성공률은 더 나빠졌다. 줄어든 품절 응답
1,206건과 늘어난 연결 실패 1,206건이 거의 일치한다.

```text
품절 응답 감소  2,415 → 1,209  = -1,206
연결 실패 증가  7,585 → 8,791  = +1,206
```

로그의 실패는 대부분 `dial: i/o timeout`이다. 이는 애플리케이션이 DB 또는 Redis를
처리하다 HTTP 오류를 반환한 기록이 아니라, k6가 TCP 연결을 만들지 못한 단계의 실패다.
또한 두 테스트 모두 설정한 20,000 VU보다 적은 VU만 실제로 준비됐다.

### 주의: Redis 선판단 코드의 성능 결과가 아니다

16:58 테스트 당시 실행 중인 `app` 컨테이너는 Redis 선판단 커밋보다 먼저 생성돼 있었다.
따라서 이 결과는 새 Redis 선판단 코드가 배포된 뒤의 성능 수치로 해석하면 안 된다.
새 이미지를 빌드·재시작한 뒤 같은 조건으로 재시험해야 한다.

## 5. 왜 Tomcat 대기열을 키웠는데 p95가 나빠질 수 있는가

`max-connections=25000`, `accept-count=5000`, `threads.max=200`은 더 많은 연결을
받아 대기시킬 수 있게 한다. 하지만 실제 요청 처리 작업자는 최대 200개다.

```text
TCP 연결
→ Tomcat 연결 대기열
→ 최대 200개 요청 처리 스레드
→ Redis / MySQL
```

따라서 병목이 해소되지 않은 상태에서 대기열만 늘리면 연결 거절 대신 긴 대기가 발생해
p95·p99가 커질 수 있다. Hikari 풀도 현재 실행 컨테이너에서는 10개였으므로, 성공 요청의
동기 DB 저장이 밀리면 200개 요청 처리 스레드가 DB 커넥션을 기다릴 수 있다.

Tomcat 또는 Hikari 수를 먼저 크게 늘리는 것은 해결책이 아니다. 실제 부하와 DB CPU,
Hikari pending, MySQL lock wait를 함께 보고 제한값을 조정해야 한다.

## 6. 다음 재검증 순서

1. Redis 선판단 코드가 포함된 앱 이미지를 새로 빌드하고 컨테이너를 재시작한다.
2. `VERIFY_INDIVIDUAL_PERSISTENCE=false`로 발급 부하와 개별 조회 부하를 분리한다.
3. 1,000 → 3,000 → 5,000 → 8,000 VU로 단계적으로 올려 서버 지표를 기록한다.
4. 20,000 VU는 k6 발생기를 여러 대로 나누고 사용자 ID 범위를 분리한다.
5. 각 실행에서 다음을 동시에 확인한다.

   - `coupon_claim_success_total == 재고`
   - `coupon_claim_sold_out_total == VU - 재고`
   - transport failure와 예상 밖 응답은 0건
   - `user_coupon` 실제 수는 재고와 같음
   - Claim p95, Hikari active/pending, MySQL lock wait, 서버 CPU

6. 단일 k6에서도 `dial: i/o timeout`이 남으면 k6 PC만의 문제가 아니라고 단정하지
   않는다. 서버 OS의 TCP backlog, Docker 포트 포워딩, 서버와 k6 사이 네트워크 구간을
   함께 점검한다.

## 발표용 결론

쿠폰 발급의 정합성 문제는 Redis Lua와 짧은 DB transaction으로 해결한다. 대량 트래픽의
핵심은 모든 요청을 DB로 보내지 않는 것이다. 품절·중복은 Redis에서 끝내고 실제 당첨자만
DB에 저장하면, 즉시 쿠폰 발급이라는 사용자 경험을 유지하면서 DB 병목을 줄일 수 있다.

다만 20,000 VU 결과의 대다수가 TCP 연결 단계에서 실패하면 그것은 DB 성능 시험이 아니다.
먼저 최신 서버 코드 배포와 신뢰할 수 있는 부하 발생기 구성을 갖춘 뒤, DB·Redis·네트워크
병목을 분리해 측정해야 한다.
