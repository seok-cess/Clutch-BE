# ADR-002: MySQL 기준 Redis 쿠폰 재고 재구축

- Status: Accepted
- Date: 2026-08-20
- Decision Makers: 쿠폰 발급 담당자

## Context

쿠폰 발급은 Redis Lua로 재고를 차감하고 중복 당첨을 막는다. Redis가 중단되면
정확한 재고 차감이 불가능하며, 재고 키 또는 전체 데이터가 유실되면 Redis 값만으로
남은 수량과 기존 당첨자를 알 수 없다.

기존 `CouponStockInitializer`는 MySQL의 `quantity - successCount`로 재고 키 하나만
초기화했다. 발급 사용자 Set을 복구하지 않고 복구 중 발급을 차단하지 않아 전체 장애
복구 절차로 사용하기에는 부족했다.

## Decision

- Redis 상태가 `READY`가 아니면 쿠폰 발급을 중단하는 Fail Closed 방식을 사용한다.
- 장애 중 요청 순서는 저장하거나 보존하지 않는다.
- 실제 `user_coupon`을 최종 발급 기준으로 사용한다.
- 복구 전에 이벤트 항목의 `success_count`, `SUCCEEDED` 발급 요청 수와 실제
  `user_coupon` 수가 같은지 검증한다.
- 회차별 성공 요청 사용자와 실제 쿠폰 사용자도 같은지 검증한다.
- 검증을 통과한 경우에만 Redis 재고와 `claimed-users` Set을 Lua로 함께 교체한다.
- Redis 연결 회복을 주기적으로 확인해 자동 복구하고, 실패 시 관리자 API로 상태를
  확인하고 다시 실행할 수 있게 한다.
- 데이터 불일치가 발견되면 자동 복구를 중단하고 `FAILED` 상태를 유지한다.
- 현재 복구 상태는 애플리케이션 메모리에 저장하며 단일 인스턴스를 기준으로 한다.

## Alternatives Considered

### 장애 중 요청을 Kafka에 저장

요청 순서를 보존할 수 있지만 즉시 발급 결과를 제공할 수 없고 중복 처리와 재처리
정책이 복잡해져 현재 동기 발급 결정과 맞지 않는다.

### Redis 데이터만 영속화하여 복원

AOF와 Docker volume은 일반 재시작에서 데이터 유실 가능성을 낮추지만 파일 손상,
volume 유실과 장애 직전 미반영 데이터를 완전히 해결하지 못한다.

### `success_count`만 기준으로 재고 복구

계산은 빠르지만 실제 사용자 쿠폰 생성 결과와 어긋난 상태를 발견하지 못한다.

### Redis 장애 중 MySQL로 직접 발급

발급을 계속할 수 있지만 대량 요청이 MySQL 재고 행과 연결에 집중되고, Redis 경로와
MySQL 경로 사이의 동시성 정합성을 새로 해결해야 한다.

### 관리자 수동 복구만 사용

구조는 단순하지만 운영자가 대응할 때까지 발급 중단 시간이 길어진다. 자동 복구를
기본으로 사용하고 수동 재시도를 보조 수단으로 둔다.

## Consequences

- Redis 상태가 불확실할 때 초과 발급보다 발급 중단을 우선한다.
- Redis 복구 후 MySQL의 확정된 실제 쿠폰을 기준으로 남은 재고를 재구축한다.
- 장애 중 요청한 사용자는 복구 후 다시 요청해야 하며 기존 순서는 보장하지 않는다.
- MySQL 데이터가 어긋나 있으면 잘못된 자동 복구 대신 운영자 확인이 필요하다.
- 복구 시에만 MySQL을 조회하며 정상 재고 조회와 갱신은 계속 Redis만 사용한다.
- 다중 애플리케이션 인스턴스에서는 복구 상태와 실행을 조정할 별도 잠금이 필요하다.

## Follow-up

- 복구 성공·실패 횟수와 소요 시간 메트릭 추가
- 관리자 API 인증 정책 확인
- 다중 인스턴스용 MySQL 복구 잠금 또는 복구 상태 테이블 검토
- Redis Sentinel 또는 Cluster를 이용한 장애 시간 단축 검토
