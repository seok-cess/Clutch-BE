# ADR-001: 실제 쿠폰 생성 기준의 동기 발급

- Status: Accepted
- Date: 2026-08-19
- Decision Makers: 쿠폰 발급 담당자

## Context

기존 쿠폰 발급 요청은 Redis에서 재고와 당첨자를 확보한 뒤 요청을 `PENDING`으로 저장하고, Kafka를 통해 지갑 영역이 나중에 `user_coupon`을 생성하는 비동기 흐름이었다.

이 흐름에서는 API 응답 시점에 사용자가 실제 쿠폰 발급 성공 여부를 알 수 없으며, Kafka 또는 지갑 처리 장애가 발생하면 Redis 당첨 기록과 발급 요청은 존재하지만 실제 쿠폰은 없는 상태가 발생할 수 있다. 서비스 요구사항은 사용자가 발급 성공과 실패를 즉시 확인하고, 쿠폰 생성 실패 시 다음 발급 회차에 다시 참여할 수 있도록 하는 것이다.

## Decision

- Redis Lua 실행 성공을 최종 발급이 아닌 재고와 당첨자 자리 확보로 정의한다.
- `user_coupon`이 MySQL에 생성된 시점을 최종 발급 성공으로 정의한다.
- 발급 요청 저장, 이벤트 항목 성공 수량 증가, `user_coupon` 생성과 발급 결과 Outbox 저장을 하나의 MySQL transaction에서 처리한다.
- `user_coupon` 저장을 명시적으로 flush한 뒤 발급 요청을 `SUCCEEDED`로 변경하고 API 응답에 `couponId`를 포함한다.
- transaction rollback 후 Redis 재고를 복원하고 당첨자 집합에서 사용자를 제거한다.
- Kafka는 실제 쿠폰 생성의 필수 경로에서 제외하고 발급 결과 후속 전달에 사용한다.
- 기존 Kafka 발급 소비 메서드는 기존 이벤트와 테스트 호환을 위해 당분간 유지한다.

## Alternatives Considered

### Kafka 비동기 발급 유지

API 요청 처리 시간이 짧고 모듈 결합도가 낮지만, 사용자가 실제 쿠폰 생성 결과를 즉시 알 수 없다. Kafka 지연이나 장애 시 `PENDING` 상태가 장시간 유지될 수 있어 현재 성공 응답 요구사항에 맞지 않는다.

### Redis 당첨을 최종 성공으로 처리

빠르게 응답할 수 있지만 MySQL 쿠폰 생성 실패 시 사용자에게 성공을 응답하고도 쿠폰이 존재하지 않는 정합성 문제가 발생한다.

### MySQL만 사용한 재고 동시성 제어

단일 transaction 구성이 단순하지만 대량 동시 요청이 재고 행과 데이터베이스 연결에 집중되어 DB 부하를 낮추려는 요구사항에 맞지 않는다.

## Consequences

- 사용자는 API 응답에서 실제 쿠폰 식별자와 최종 성공 상태를 즉시 확인할 수 있다.
- 성공 응답 수, 발급 요청 수, 실제 쿠폰 수와 Redis 당첨자 수를 동일하게 유지할 수 있다.
- 쿠폰 생성 실패 시 DB와 Redis를 보상해 재고 및 재참여 가능 상태를 복구할 수 있다.
- API 응답 시간에 MySQL 쿠폰 저장 시간이 포함된다.
- 발급 요청 영역이 공통 `CouponIssuer` 계약을 통해 지갑 영역의 동기 구현을 호출하므로 두 영역 사이에 명시적인 애플리케이션 계약이 생긴다.
- Kafka Outbox는 발급 자체가 아닌 후속 결과 전달의 신뢰성을 담당한다.

## Follow-up

- Redis 연결 장애를 사용자에게 즉시 전달하는 오류 응답과 운영 모니터링 추가
- Redis 재기동 시 재고와 당첨자 데이터의 자동 복구 절차 구현
- 실시간 잔여 재고 조회 및 사용자 전달 방식 확정
- 기존 `coupon.claim.accepted` 핵심 발급 경로 제거 시점 확정
- 동기 발급 지연 시간과 보상 실패 횟수 모니터링 추가
