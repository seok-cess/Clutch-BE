# 쿠폰 대량 데이터 정합성 검증 결과 — 2026-08-26

## 결론

2026-08-26 04:48:11 UTC의 읽기 전용 일관 스냅샷을 기준으로 검증했다.
가상 사용자 100만 명과 쿠폰 발급 요청 이력 300만 건 조건을 만족했으며, 참조 관계,
중복 발급, 상태 전이, 실제 쿠폰 연결과 재고 수량에 대한 모든 FAIL 검사는 통과했다.

따라서 현재 적재 데이터의 핵심 정합성은 정상이다. 다만 Java와 DB의 상태 계약 불일치
1건과 대량 집계용 인덱스 누락 1건은 후속 조치가 필요하다.

## 실행 조건

- 대상: Tailscale로 연결된 MySQL `clutch` 데이터베이스
- 방식: `REPEATABLE READ`, `START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY`
- 검증 SQL: [`../coupon-integrity.sql`](../coupon-integrity.sql)
- 개인정보 출력 및 데이터 변경: 없음
- 실행 전 안정성 확인: 약 13초 간격의 두 조회에서 요청·쿠폰 건수가 동일함

## 정합성 결과

다음 FAIL 검사는 모두 위반 건수 0으로 통과했다.

- 사용자·이벤트·회차·이벤트 항목·발급 요청의 고아 참조
- 발급 요청과 사용자 쿠폰의 사용자·이벤트·회차·항목 관계 불일치
- 성공 요청에 쿠폰이 없거나 실패 요청에 쿠폰이 연결된 경우
- 동일 사용자·회차의 중복 요청 및 중복 쿠폰
- 수량 초과 발급, 잘못된 재고 범위, `success_count` 불일치
- 요청 및 쿠폰 상태와 완료·사용·취소 시각 불일치
- 잘못된 회차 기간과 상태
- 장시간 남은 PENDING 요청과 만료 후 OPEN 회차

첫 실행은 직전 1만 건 부하 테스트의 쿠폰 저장 직후 수행되어 이벤트 항목 1개의
`success_count`가 실제 쿠폰 수보다 잠시 뒤처졌다. 5초 주기
`CouponSuccessCountSynchronizer`가 보정한 뒤 새 스냅샷으로 재실행했고 위반 건수 0을
확인했다. 이는 데이터 유실이 아니라 요청 경로에서 공통 행 갱신을 분리한 구조에서
발생하는 일시적 최종 일관성이다.

## WARN과 후속 조치

### 1. 발급 요청 상태 계약 불일치

- 실제 `CANCELLED` 요청: 13,600건
- DB 제약은 `CANCELLED`를 허용한다.
- Java `ClaimRequestStatus`는 `PENDING`, `SUCCEEDED`, `FAILED`만 정의한다.

해당 행을 JPA 엔티티로 조회하면 enum 변환 오류가 발생할 수 있다. `CANCELLED`가 현재
도메인의 유효 상태라면 Java enum과 상태 전이 규칙을 DB 계약에 맞춰야 한다. 유효하지
않다면 기존 데이터의 생성 경로와 보정 정책을 먼저 결정해야 하며, 검증 과정에서는
데이터를 자동 수정하지 않았다.

### 2. 이벤트 항목 기준 인덱스 누락

`user_coupon(coupon_event_item_id)`를 선두 컬럼으로 하는 인덱스가 없다. 현재
`CouponSuccessCountSynchronizer`는 모든 이벤트 항목마다 실제 쿠폰 수를 집계하므로,
데이터가 커질수록 불필요한 전체 탐색과 DB 부하가 증가할 수 있다.

후속 작업에서는 실행 계획을 확인한 뒤 Flyway migration으로 해당 인덱스를 추가하고,
스케줄러 집계를 항목별 반복 쿼리 대신 한 번의 그룹 집계로 바꾸는 방안을 검토한다.

## 후속 조치 결과

검증 이후 다음 조치를 반영했다.

- Java `ClaimRequestStatus`에 `CANCELLED`, `UserCouponStatus`에 `EXPIRED`를 추가해
  기존 DB 상태를 JPA와 관리자 발급 내역 API에서 안전하게 조회하도록 했다.
- `user_coupon(coupon_event_item_id)` 인덱스를 Flyway V16으로 추가했다.
- 이벤트 항목별 반복 COUNT를 단일 GROUP BY 집계로 변경했다.
- MySQL 실행 계획에서 `idx_user_coupon_event_item`과 `Using index`를 확인했다.
- 다중 인스턴스 중복 집계를 MySQL named lock으로 차단하고 실행 메트릭을 추가했다.

따라서 이 결과 문서의 두 WARN은 후속 구현 기준으로 해소됐다. 원본 스냅샷에서
관찰한 건수와 당시 판정은 검증 이력 보존을 위해 변경하지 않는다.
